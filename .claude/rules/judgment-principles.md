# 判定・検証の判断原則

判定・検証を行う際に守る 3 つの規律。要素は原文の逐語を保持する。

## 1. 安全側に倒す

「現状 0 hit だから実装しない」判断はせず、安全側に倒す。

実例: 2026-08-06 のユーザー裁定で、根拠不足のまま省略した判断 2 件を是正し、件数を見ずに沈黙していた判断をさらに 2 件検出した。

## 2. 到達可能性の判定

到達可能性は「参照 0 件」でなく「発火しうる経路が無い」で判定する（削除・影響判定の規約）。当たるべき経路＝動的ロード / subprocess / 名前写像 / 設定 JSON 登録・monkeypatch 対象の導出タイミング（呼び出し時か import 時か）・ローカル skip テストは「実行されていない」前提で判定・探索ツールの射程を明示する（gitignored 配下は rg で 0 件・grep -rn でヒットし、真偽が道具で反転する）。

実例: 2026-08-13 に同型の誤判定が実働で再演し、CI 5 構成全赤を招いた。

## 3. 機械走査の 3 点申告

機械走査を名乗るときは 3 点を申告する: (a) 走査対象の形式を全部数えて申告（表行・引用ブロック・見出し・本文） (b) 版順の根拠を明示（ファイル名順とは限らない） (c) 検証が測っている性質を書く（「バイト一致」は書き写しの正確さであって拾う版の正しさではない）。

実例: 2026-08-07 の集約・移設作業で「畳む」工程の取り落としを 3 回連続で実測した。
