# 判定・検証の判断原則

判定・検証を行う全 role が、結論を出す前と報告する前に守る規律。

## 1. 安全側に倒す

「現状 0 hit だから実装しない」判断はせず、安全側に倒す。

実際に到達できなかった制御を、不要だったと畳まない。「測れなかった」と「不要だった」を分けて書く（§2 の具体化でもある）。

## 2. 到達可能性の判定

到達可能性は「参照 0 件」でなく「発火しうる経路が無い」で判定する（削除・影響判定の規約）。当たるべき経路＝動的ロード / subprocess / 名前写像 / 設定 JSON 登録・monkeypatch 対象の導出タイミング（呼び出し時か import 時か）・ローカル skip テストは「実行されていない」前提で判定・探索ツールの射程を明示する（gitignored 配下は rg で 0 件・grep -rn でヒットし、真偽が道具で反転する）。

誤判定は CI の全構成を赤にしうる。

テストの実行を省く根拠に、変更ファイルの一覧を使わない。そのテストが何を読むかを確かめる。

## 3. 機械走査の 3 点申告

機械走査を名乗るときは 3 点を申告する: (a) 走査対象の形式を全部数えて申告（表行・引用ブロック・見出し・本文） (b) 版順の根拠を明示（ファイル名順とは限らない） (c) 検証が測っている性質を書く（「バイト一致」は書き写しの正確さであって拾う版の正しさではない）。

## 4. 原因の切り分けと計測

2 つの実測を比べて原因を決める前に、違う条件を全部数える（交絡）。2 つ以上違えば 1 つずつ変えて測る。

パイプやフィルタで数えるときは、左側が実行できたかを確かめる。当たるはずの対象で 1 以上が出ることを先に見る（0 件は左側の失敗でも出る）。

## 5. 待ち時間とぶれるテスト

待ち時間・時間切れで順序や同期を作らない（テストでも、待ち時間で同期を取らない）。時間切れは上限としてだけ使う。

ぶれるテストを、時間待ちの型やフレークと決めて片付けない。落ちた回の材料（ログは上書きしない）で仕組みを確かめる。同じテストが続けて別の形で落ちたら 1 つずつ直さず、そのテストが要るか・時間がその性質に要るかから考え直す。

## 6. 検証の基盤と緑の報告

検証の基盤（ゲート・検査・計測の仕組み）が本番の環境で正しく動くことを、模擬の環境だけで保証しない。本番の経路で 1 回実測する（テストの検知力の実証を写しで行うことはこれに当たらない）。

ゲートの緑は、そのゲート自身の出力（exit code・件数）を見てから言う。止まった実行や別のゲートの出力から推した結果は「未確認」と書く。

「測れない」「検出点が無い」と書く前に、既存テストが何を測っているかを現物で見て、根拠を同じ箇所に添える。

検証が安全だという根拠に、その検証の対象の機能を使わない（循環した安全保証）。

## 7. 集合と規約の当て方

集合は列挙でなく、集合を決める規則で書く。件数は検算に使い、件数で集合を書かない。

規約は字面の一致でなく、「何を守るための規則か」で当てる。
